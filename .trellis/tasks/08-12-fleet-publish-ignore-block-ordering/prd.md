# Regenerate the managed ignore block before the fleet publish work commit

## Goal

`sd-ai-command-pack-fleet-publish.py` builds the work commit before anything
regenerates the pack-managed `.obsidian-kb` block in the consumer's
`.gitignore`. When a release changes that block, the consumer's tree only goes
dirty later, when `sd-ai-command-pack-housekeeping.sh` runs the spec-KB updater
at the merge gate. By then the completion bundle is already published, and the
change cannot be folded into it.

Observed in campaign `refresh-0.71.2-20260813T014138Z-c3` on both selected
consumers. Release 0.71.2 rewrites the block's marker comment from
`# Generated by scripts/sd-ai-command-pack-update-spec-kb.py. DO NOT EDIT MANUALLY.`
to `# Generated by sd-ai-command-pack. DO NOT EDIT MANUALLY.`. Each consumer
required a `git reset --hard`, a rebuilt bundle, an operator-run force push, and
a second review and CI cycle.

## Why it cannot be repaired forward

`.gitignore` is not a bookkeeping path, so a completion receipt whose span
contains it is rejected with `bundle_scope_invalid`. A second completion bundle
covering the later commit is rejected with `completion_archive_move_missing`,
because the archive move can only happen once per task. The only supported shape
is one bundle whose work commit already carries the change, so the fix must move
the regeneration earlier rather than add a commit later.

## Requirements

1. Before `work_commit()`, `publish()` must regenerate the consumer's managed
   ignore block so any resulting `.gitignore` change is captured by the work
   commit's `git add -A`.
2. The regeneration must invoke the consumer's installed
   `scripts/sd-ai-command-pack-update-spec-kb.py` with the same argument form
   `sd-ai-command-pack-housekeeping.sh` uses, so the two produce identical
   `.gitignore` content. Housekeeping passes no `--if-present`, so publish must
   not pass it either; `--if-present` returns early when `.obsidian-kb` is
   absent and would skip the ignore block that housekeeping still writes.
   The helper resolves its own root from the current working directory via
   `git rev-parse --show-toplevel`, so it must be invoked with the consumer
   worktree as cwd, not the source checkout.
3. `.gitignore` must be accepted by the dirty-tree allowlist, for the case where
   the operator already ran housekeeping and left the block regenerated before
   publish starts. Today that tree is refused. Allowlisting alone is not the
   fix: on an untouched tree the file is still clean at publish time, so without
   requirement 1 there is nothing to allow.
4. A consumer that does not ship the updater, or whose KB target is read-only,
   must still publish. The `.obsidian-kb` folder is regenerable and ignored, so
   its refresh failing is not a reason to fail a pack refresh. Publish must
   surface the condition rather than abort.
5. Behavior must not change for a consumer whose ignore block is already
   current: no new commit content, no new failure mode, and an unchanged
   completion receipt shape.

## Constraints

- Do not widen `assert_trellis_only_delta`. It guards the bookkeeping span
  between `h1` and `h3`; `.gitignore` belongs in `h1`, before that span opens.
- Do not add a second commit, a second bundle, or any path that depends on
  rewriting a pushed branch.
- The change is confined to the source checkout's publish helper. It takes
  effect for the next campaign without a new pack release, because campaigns run
  this script from the source tree rather than from an installed copy.

## Acceptance Criteria

- [ ] `publish()` regenerates the managed ignore block before `work_commit()`.
- [ ] The invocation matches `sd-ai-command-pack-housekeeping.sh`'s argument
      form, verified by reading both call sites.
- [ ] `.gitignore` is in the dirty-tree allowlist.
- [ ] A missing updater or a read-only KB target is reported and does not fail
      the publish.
- [ ] On a consumer whose block is already current, the published bundle is
      byte-identical to what the current code produces.
- [ ] A consumer publish whose block is stale produces one work commit
      containing the `.gitignore` change and a `valid` completion receipt, with
      no force push required.

## Verification

The decisive check is the last criterion, and it needs a consumer whose block is
stale. Both consumers in campaign `-c3` are now at 0.71.2 and no longer
reproduce it. Of the five consumers still on 0.71.1, any whose `.gitignore`
still carries the old marker reproduces it; confirm by grepping their
`.gitignore` for the pre-0.71.2 marker string before relying on them as the
test. If none does, the criterion is verified by the next release that changes
the block, and that gap must be stated rather than papered over with a passing
unit test that does not exercise the ordering.

## Notes

The same ordering already works correctly for `docs/repomix-map.md`:
`regenerate_repomix_post_archive()` runs before `work_commit()`, and
`docs/repomix-map.md` is in `DEFAULT_ALLOWED_PREFIXES`. This task applies that
established shape to the second piece of generated content, and places the new
step next to it — after `check_preconditions()`, before `work_commit()`.

Two properties make the earlier placement safe, both confirmed by reading
`sd-ai-command-pack-update-spec-kb.py`:

- The ignore block is a module-level constant pair
  (`KB_IGNORE_BLOCK_START` / `KB_IGNORE_BLOCK_END` around a fixed
  `/.obsidian-kb` entry). Its text does not depend on task state, so running the
  helper before the archive move yields the same block as running it after.
  Only the `.obsidian-kb` copy folder depends on repository content, and that
  folder is ignored by the very block being written.
- On a consumer that has neither the folder nor the block, the helper creates
  both. The folder is then ignored, and the added block is a tracked
  `.gitignore` change that requirement 1 places inside the work commit. That is
  the same end state housekeeping reaches today, reached one commit earlier.
