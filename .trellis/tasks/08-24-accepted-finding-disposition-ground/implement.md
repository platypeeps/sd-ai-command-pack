# Implementation plan — accepted-finding disposition ground

Single edit site: `templates/scripts/sd-ai-command-pack-review-local.py`.
The copies under `scripts/`, `plugins/sd/bin/`, and
`plugins/sd/machine-payload/scripts/` are byte-identical mirrors regenerated by
`make generate` — never hand-edit them.

Branch: `task/accepted-finding-disposition-ground` off `main`.

## Order

Tests before implementation, because the second acceptance criterion is
specifically "a test that would fail if accepted were an alias of rebutted" —
that test has to be seen failing for the right reason before the code exists.

### 1. Write the failing tests

`tests/test_review_stage.py`, beside the existing disposition tests
(`dispositionCitation` appears at `:1782` and `:2033`; follow their shape).

- [ ] **Release paired with block.** One `high` finding, good citation, claim
      true. Same test asserts both halves: no disposition to
      `remoteGate.state == "blocked"`, `reason == "actionable-local-findings"`;
      then `accepted` to `remoteGate.state == "eligible"`.
- [ ] **Not an alias of rebutted.** Assert `finding["disposition"] ==
      "accepted"`, `finding["dispositionReason"]` present and equal to the
      supplied text, `"dispositionCitation" not in finding`, and that the
      receipt's `accepted` count is 1 while `dispositioned` stays 0.
- [ ] **Bound enforced**, each raising `ReviewInputError`, none a traceback:
      `accepted` with no `@`; empty reason; reason over 500 characters; reason
      containing a control character; reason containing `=`.
- [ ] **Family evidence still rejects `accepted`.** A pin test submitting
      `--family-evidence` with `disposition: "accepted"` and asserting
      `ReviewInputError`. Without it, a later hand adds `accepted` to
      `FINDING_DISPOSITIONS` for symmetry and silently widens a surface
      this task deliberately left closed.
- [ ] **The `=` case gets its own diagnostic** — assert the message is the
      `accepted`-specific one, not the generic "local dispositions must use…".
      Without this the generic message is what a plain typo produces, and it
      names the wrong problem.

**Gate:** `make test` fails, and each new test fails for its stated reason
(read the assertion text, do not just count reds).

### 2. Vocabulary and parsing

- [ ] `FINDING_DISPOSITIONS` (`:83`) is **left alone**. Its only use is
      `_parse_family_finding` (`:924`), which validates `--family-evidence`,
      not receipt findings. Widening it would extend an unrelated input
      grammar. See `design.md`.
- [ ] `LOCAL_DISPOSITION_VALUES` (`:91`) gains `accepted`; extend the comment
      above it — it currently explains the two grounds and their trust posture,
      and a third ground with a different basis (the claim is true) belongs in
      that explanation.
- [ ] `_parse_local_dispositions` (`:2001`): `accepted` requires the `@`
      payload; parse via a new `_parse_accepted_reason`. The existing
      `elif marker:` branch that raises "only miscited accepts a citation" must
      be updated — it is now wrong as written.
- [ ] `_parse_accepted_reason`: non-empty, `len <= 500`, no `ord < 32`, no `=`.
      Returns `{"disposition": "accepted", "reason": reason}`.
- [ ] `_reject_local_disposition` (`:2042`): add the `accepted` + `=` branch
      alongside the existing miscited one, and update the generic message to
      name all three grammars.

### 3. Application to the finding

- [ ] `_apply_local_dispositions` (`:2091`): alongside the `miscited` branch,
      write `finding["dispositionReason"] = record["reason"]` for `accepted`.
      Update the docstring — it explains why the bare vocabulary member is
      stored rather than the raw argument, and that reasoning now covers a
      second payload-carrying ground.
- [ ] Nothing to do for `disposition["localDispositions"]` (`:2159-2161`, and `:2422`), and that

### 4. Counting and the gate

- [ ] `_disposition_counts` (`:2200`) returns a 4-tuple. Test `accepted`
      **before** the `LOCAL_DISPOSITION_VALUES` membership branch — with
      `accepted` now in that set, wrong order silently folds it into
      `dispositioned` and the alias test is what catches it.
- [ ] Both call sites unpack four: `:2152` (`_redispose_receipt`) and `:2400`.
- [ ] Both write sites gain the field: `:2156-2158` and `:2417-2419`.
- [ ] **Both `_remote_gate` calls pass `accepted=accepted`** — `:2163` and
      `:2424`. Unpacking the fourth value and writing the count while
      leaving the call sites alone is the silent failure here: the count
      appears in the receipt, the new ladder rung never fires, and the
      gate reports the wrong reason while every count looks right.
- [ ] `_remote_gate` (`:2226`) gains `accepted: int = 0`, and a new **first**
      rung on the eligible ladder returning
      `{"state": "eligible", "reason": "local-findings-accepted"}` — ahead of
      the `dispositioned` rung, so a waiver is never masked by better news.
      It must not appear in the blocking condition.

**Gate:** `make test` green, including the pre-existing suite unchanged. A
receipt with no `accepted` disposition must produce byte-identical output to
today apart from the new zero-valued count — if an existing test moves, stop
and find out why.

grammar is documented, and `sd-ai-command-pack-review-local.py` is on its
`INTERNAL_ALLOWLIST` and exempt regardless. Acceptance criterion 4 is therefore
a manual check — treat it as unmet until read, not as covered by `make test`.

- [ ] `templates/.agents/skills/sd-review/SKILL.md`, in the disposition passage

      third ground, its grammar, the required reason, and — importantly — the

- [ ] Not `templates/docs/SD_AI_COMMAND_PACK.md`: it contains no

## Rollback

Each stage is a separate commit on the task branch, so any stage reverts alone.

The one irreversible-by-revert step is the **version bump plus ledger refresh**
— reverting the payload without refreshing the ledger leaves a stale digest and
`make check` red. If stage 6 has to be undone, revert payload and ledger
together and re-run `make release-prep`.

Nothing here touches consumer repositories until a rollout, and a rollout is a
separate decision. `install.py --force` is never used against a consumer.
