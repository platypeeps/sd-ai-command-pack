# Design — retire the pre-0.6.16 vendored Trellis compatibility layer

## Authoring boundary

`templates/**` is the source of truth (CONTRIBUTING, "Release And Payload
Rules"). Every shipped script exists in four byte-identical copies:

```
templates/scripts/<name>          <- edit here
scripts/<name>                    <- refreshed by `make sync` (install.py . --force)
plugins/sd/bin/<name>             <- regenerated by `make generate`
plugins/sd/machine-payload/scripts/<name>
```

Verified identical at task start with `cmp` for both scripts in scope. Editing
any copy other than `templates/` is a defect; the generators overwrite it.

`.trellis/spec/**` and `.trellis/tasks/**` are repo-local, not shipped, so they
do not participate in the mirror or trigger a payload version bump.

## R1 — the compatibility spec

Rewrite three sections of
`.trellis/spec/tooling/vendored-trellis-compatibility.md`:

**Version-spread reality → Supported floor.** Replace the "MUST work against
both … and <=0.6.7" rule with: pack wrappers target the vendored Trellis build
`0.6.16-sd.7`; a checkout below the floor is a violation to be upgraded, not a
configuration to be supported. This inverts the maintenance default — the
open-ended clause made every future wrapper carry compatibility branches
indefinitely, with no stated condition under which they could ever be removed.
A floor names that condition.

State the floor as an **identity, not a range**, and say why in the spec. The
fleet build `0.6.16-sd.7` carries a prerelease segment: under semver it sorts
*below* `0.6.16`, so the natural-looking rule "require `>=0.6.16`" would classify
all nine converged repositories as non-compliant. Nothing in the pack compares
Trellis versions programmatically today, and this spec is the place to keep it
that way — the floor is checked by reading `.trellis/.version` and comparing it
to the recorded build string, not by evaluating a range.

**Signatures.** Re-pin the table from "0.6.14" to the floor, and record the
facts this task depends on, each verified against the runtime:

- `resolve_commit_subject` peels with `^{commit}` and returns `EMPTY_SUBJECT`
  (`"(empty subject)"`) for a commit with an empty message; `None` only when git
  cannot resolve the object at all.
- `build_commit_evidence` fails before any mutation on an unresolvable OID.
- `escape_markdown_cell` collapses whitespace, then escapes `\` and `|`.
- `MAX_SUBJECT_LEN = 500`.
- `_render_bullet_section` applies its `bullet_prefix` unconditionally — the
  reason Testing/Next Steps cannot be delegated (PRD, "does NOT remove").
- `create` accepts `--base-branch`; without it, base resolves from
  `origin/HEAD`, falling back to the checked-out branch.

**Upgrade procedure.** The current text prescribes `npx
@mindfoldhq/trellis@<current> update`. That is wrong for this fleet: the runtime
is a fork (`github.com:sdelmas/Trellis`, package version `0.6.16-sd.7`) that
shares the npm *name* but is never published — npm `latest` is `0.6.15` and no
`-sd` tag exists. Rewrite the procedure to run `trellis update` from a built
fork checkout, and state the hazard explicitly: a CLI installed from npm is
below the floor, and running `trellis update` from it downgrades the vendored
tree. Everything else in the procedure (hash-manifest conflict classification,
sandbox-clone dry run, the acceptance checks) is distribution-independent and
stays.

## R2 — status collector fallback

`collect_trellis` in `templates/scripts/sd-ai-command-pack-status.py` runs
`task.py current --json` and then branches three ways. At the floor, `--json` is
always present and always emits an object, so branches 2 and 3 are unreachable.

Collapse to: run `current --json`; on non-zero exit or unparseable output, treat
the active task as absent. The failure mode changes from "silently fall back to
prose parsing" to "report no active task", which is the correct answer when the
documented interface did not answer.

**R6 rides here.** The payload already carries `versions.trellis`
(`read_version(repo / ".trellis/.version")`), and `render_fleet` prints
`pack <v>` / `pin <v>` without it. Add the Trellis version to the rendered row.
No collection change — this is a rendering-only fix, which is why it is folded
in rather than filed separately.

**`stale` adoption.** `current --json` returns `{"current_task", "source",
"stale"}`. The collector reads only `current_task.dir`. Surface `stale` in the
JSON payload and the human report: a stale active-task pointer is precisely the
kind of drift a status report exists to show.

### Declined: `task.py list --json`

The collector hand-walks `.trellis/tasks/*/task.json`. `list --json` returns
`dir/id/title/status/display_status/priority/assignee/parent/children/package`,
which covers every field `task_record` reads, and counts agree (81 vs 81).

Declined anyway. The walk is not a version workaround — it predates and is
independent of the compat layer, so it is out of this task's stated scope. It
also costs one subprocess per repository in fleet mode (nine today) to replace a
filesystem read that already works, and the walk carries explicit symlink
hardening that would become implicit. Schema-drift resistance is the real
argument for switching; it is not strong enough to churn a working collector
inside a removal task. Recorded here so the option is not re-derived from
scratch later.

## R3 — record-session commit rows

Today the wrapper resolves every subject itself, invokes `add_session.py`
without them, and then rewrites each `| \`<hash>\` | … |` row in the written
journal with a regex, escaping the cell as `subject.replace("|", "\\|")`.

That post-write rewrite is strictly worse than what it overwrites. Both escape
a pipe identically; on everything else the wrapper is the weaker of the two:

| Subject contains | `escape_markdown_cell` | wrapper's overwrite |
|---|---|---|
| a pipe | escaped | escaped (agrees) |
| a backslash | escaped | left raw |
| runs of whitespace or a newline | collapsed to single spaces | preserved, can break the row |
| more than 500 characters | truncated at `MAX_SUBJECT_LEN` | untruncated |

So the change is a removal *and* a bug fix. Delete `JOURNAL_COMMIT_CELL_RE`-based
row patching, the `row_re` construction, and the `_row_replacement` callable
(whose entire existence is a comment about backslash handling that
`escape_markdown_cell` makes moot).

Keep the pre-flight `commit_subject()` probe. It is no longer needed to *supply*
the subject, but it preserves the wrapper's documented exit-code contract: an
unknown hash exits `2` (argument error) before anything is written, whereas
delegating would surface `add_session.py`'s non-zero exit as the wrapper's `1`.
The probe's `"(empty subject)"` fallback is byte-identical to the runtime's
`EMPTY_SUBJECT`, so the two agree on the empty-message case.

`JOURNAL_COMMIT_CELL_RE` itself stays — `recorded_commit_hashes()` uses it to
scan existing journals for `derive_work_commits`, which is unrelated.

The wrapper has never passed `--commit-subject` and does not start now; it
supplies the OIDs and lets the runtime resolve them. The override flag is worth
knowing about (it is the documented escape hatch for an OID that cannot be
resolved locally) but this wrapper fails fast on that case instead, so it has no
use for it.

**Keep one integrity assertion.** The current row loop doubles as a check: it
returns an error when a hash it asked for has no row in the written journal.
That check is not version-compatibility machinery and should survive the
removal — it catches a runtime that silently dropped a commit. Replace the
regex rewrite with a cheap presence assertion (each requested OID appears in the
session block), keeping the failure mode without the rendering.

The placeholder sweep over `PLACEHOLDERS` stays as a cheap end-gate.

## R4 — `create --base-branch`

Verified live: `task.py create --base-branch main` succeeded at task creation
for this very task, and `task.json` carries `base_branch: "main"`.

Two surfaces to correct:

- `templates/scripts/sd-ai-command-pack-review-preflight.mjs` — the
  `task_base_branch_invalid` remediation string tells the reader not to use
  `create --base-branch` "which the older vendored task_store.py rejects as an
  unrecognized argument". Drop that clause. `set-base-branch` remains the
  documented *repair* for an already-created task, which is what this message is
  about; only the false warning goes.
- `templates/.agents/skills/sd-fleet-refresh/SKILL.md` — replace the mandatory
  post-create `set-base-branch` step and its four-sentence rationale with
  `create --base-branch <default-branch>`. This is a correctness improvement,
  not just a simplification: the old sequence left a window in which `task.json`
  carried the refresh branch as its base.

## Rollout / rollback

One PR, one revert point. Every change is either a deletion of an unreachable
branch, a documentation correction, or a rendering addition. The single
behavioral change visible to a user is the commit-cell escaping in R3, which is
a strict improvement covered by a new test.

Rollback is `git revert` of the merge commit; nothing here writes migrations,
persistent state, or consumer-side files. Consumers are unaffected until the
next pack release reaches them, and the floor they would need to satisfy is the
version they already run.
