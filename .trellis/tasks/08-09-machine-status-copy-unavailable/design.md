# Design: reconcile agreeing duplicate plugin registrations

Implements `prd.md` in this directory. No new module, no new surface: two
existing resolvers change the question they ask.

## The shape of the change

Both sites today match entries by plugin id and then refuse on cardinality:

```python
if len(matches) > 1:
    # refuse
```

Cardinality is the wrong predicate. Neither site consumes the entry — each
consumes exactly one *field* of it, and multiple entries carrying the same
value for that field are not ambiguous. The fix replaces "how many entries
matched" with "how many distinct values of the field I need did they carry".

| site | field consumed | today | after |
| --- | --- | --- | --- |
| `scripts/sd-ai-command-pack-status.py:1726` | `version` | refuse if entries > 1 | refuse if distinct versions > 1 |
| `scripts/sd-ai-command-pack-pack-update.sh:145` | `installPath` | refuse if entries > 1 | refuse if distinct paths > 1 |

Neither site should reconcile the other's field. `status.py` never reads
`installPath`; the updater never reads `version`. Widening either to check both
would invent a refusal neither needs.

## D1 — the reconciliation rule

For the consumed field, collect the distinct non-empty values across all
matching entries, then branch on that count:

- **0** — every match omitted or blanked the field. This is the existing
  no-value path and keeps its existing outcome: `status.py` returns
  `unavailable` with "carries no version"; the updater exits `13`.
- **1** — the value. This is the new behaviour, and it is what the live
  three-entry listing hits.
- **more than 1** — refuse, with a diagnostic naming the conflict rather than
  the count.

The single-entry cases fall out unchanged: one entry with a version yields one
distinct value, one entry without yields zero. That is deliberate — this change
should be invisible to every listing that works today.

The docstring's reasoning at `scripts/sd-ai-command-pack-status.py:1699` — "A
guess here would let a broken `claude` masquerade as an up-to-date machine" —
survives intact and now guards the case it was actually written for. Choosing
between `9.9.9` and `9.9.8` is a guess. Reporting `0.71.22` when that is the
only version present is not.

## D2 — the exit-code contract

Exit `12` stays, with its meaning narrowed from "the plugin is listed more than
once" (`scripts/sd-ai-command-pack-pack-update.sh:20`) to a conflict between
install paths. Rationale for keeping the number rather than retiring it:

- the conflict it names is still real and still needs its own code;
- `13` already means "matched but no usable install path", so the 12/13 split
  stays coherent; and
- nothing consumes these codes programmatically — a grep for `exit 12` across
  `docs/` and `.trellis/spec/` returns no reader, so the contract is
  documentation for an operator, and rewording it costs no compatibility.

Both the header comment at `:20` and the failure text at `:158` change. `:158`
currently instructs the operator to "resolve the duplicate install before
updating", which under the new rule would only ever be printed when the
duplicates genuinely disagree — so it becomes actionable for the first time
rather than merely accurate.

## D3 — `pluginDetail` on the reconciled path stays `null`

A reconciled listing reports the version with no detail, exactly as a
single-entry listing does. `pluginDetail` being non-null is the signal that
something needs attention; populating it with "reconciled 3 agreeing entries"
would make the healthy state look noteworthy and would train the reader to
ignore the field. Multiplicity of scoped registrations is the expected shape
after the thin migration, not an event.

## D4 — the suppressed alarm is part of the deliverable

`scripts/sd-ai-command-pack-status.py:3200` emits its reconcile-the-plugin next
step only on `comparison == "skew"`. Because `unavailable` forces
`comparison: "unknown"` upstream, that step is currently unreachable *whenever
the listing has duplicates* — including for a machine whose plugin and receipt
genuinely disagree. Restoring the version therefore restores an alarm, and the
restoration needs its own test rather than being assumed from the version fix.

## Propagation path

`templates/scripts/` is the source; `scripts/` is its byte mirror, enforced by
the `mirror.stale` finding in `scripts/sd-ai-command-pack-surface-check.py` with
`make sync` as the stated remediation. `plugins/sd/bin/` and
`plugins/sd/machine-payload/scripts/` are generated by `generate-plugin.py`.

Edit order is therefore: `templates/scripts/*` first, then `make generate` and
`make sync`, then confirm `surface-check` reports no `mirror.stale`. Editing
`scripts/` directly would be overwritten by the next sync and would leave the
template — the actual source — carrying the bug.

Because `templates/**` changes, the release payload gate applies: bump
`manifest.json` (`0.71.22` today) and add a matching top `CHANGELOG.md` heading.
`make check` does not run that gate, so it cannot catch a missing bump.

## The bootstrap problem

This fix cannot deploy itself, and that is the single operational risk worth
planning for.

`~/.agents/bin/sd-ai-command-pack-pack-update.sh` is currently byte-identical to
the source copy, so the installed updater contains the bug. After the fix is
released, refreshing the machine install means running an updater that still
refuses to run. The chicken-and-egg is real but not a deadlock — the pack source
checkout carries a working copy:

```text
bash scripts/sd-ai-command-pack-pack-update.sh
```

Design decision: do not build an escape hatch into the tool. Running the source
checkout's copy is a documented, already-available route that requires no new
code, and the situation is self-clearing — one refresh through the source copy
installs a fixed updater and every later refresh works normally. Adding a
`--force`-style override would create a permanent flag to cover a one-time
transition.

Implementation must state this route in the change's `CHANGELOG.md` entry so
the operator performing the first refresh after release does not read the
exit `12` as the new code failing.

## Rollback

Pure predicate change with no persisted state, no migration, and no schema
movement. Rollback is `git revert` plus `make generate && make sync`. A machine
already refreshed past the fix keeps working after a revert, because the
reverted code still resolves single-entry listings; it only resumes refusing
duplicates.

## Test plan

| test | site | assertion |
| --- | --- | --- |
| new | `status.py` | three entries, one version, one path reports that version and `pluginDetail is None` |
| `tests/test_status.py:3219` | `status.py` | the existing `9.9.9`/`9.9.8` case still reports `unavailable`; expected detail changes from "more than once" to the conflict wording |
| new | `status.py` | a plugin/receipt version disagreement produces the `comparison == "skew"` next step from `:3200` |
| `tests/test_pack_update.py:320` | `pack-update.sh` | `test_duplicate_entries_are_refused` inverts — it duplicates the identical entry (`dict(listing[-1])`), which is the benign shape. Split into an exit-`0` reconciliation test and a new conflicting-`installPath` test that still exits `12` |
| unchanged | both | every other discovery failure in the `tests/test_status.py:3219` case table — CLI absent, nonzero exit, malformed JSON, not an array, plugin missing, entry without a version — keeps its current outcome |

The last row is the regression guard that matters most: this change touches a
function whose whole contract is "every discovery failure reports unavailable",
and only one of its seven failure modes is supposed to move.

  `machineScope` recorded both times.

  scope — is untouched.
