# Install audit cannot check provider-config currency on any thin consumer

## Goal

`sd-ai-command-pack-install-audit.py` warns that it cannot check provider
config currency on every thin consumer in the fleet. It looks for the shipped
digest history inside the audited consumer, where a thin install never puts it,
rather than in the pack source checkout it is being run from — which does have
the file. The check is therefore disabled everywhere it was meant to apply.

## Evidence

Observed 2026-08-29 across campaign `fleet-0.71.63-20260829T025500Z`. Every
consumer is registry `mode: thin`, and every audit emits:

```
warning: cannot check provider config currency for 2 target(s):
docs/sd-ai-command-pack-provider-config-history.json is not present
```

Established facts:

- `scripts/sd-ai-command-pack-install-audit.py` defines
  `PROVIDER_CONFIG_HISTORY = Path("docs/sd-ai-command-pack-provider-config-history.json")`
  and `_provider_config_history(root)` resolves it as `root / PROVIDER_CONFIG_HISTORY`,
  where `root` is the *audited consumer*.
- A thin install writes only `.sd-ai-command-pack/manifest.json` and
  `.sd-ai-command-pack/provenance.json`. It never writes a `docs/` payload, so
  that path cannot exist in a thin consumer and the "not present" branch is
  taken unconditionally.
- The file is not missing from the project. The pack source checkout carries it
  at both `docs/sd-ai-command-pack-provider-config-history.json` and
  `templates/docs/sd-ai-command-pack-provider-config-history.json`, and it is
  generated by `.github/scripts/generate-provider-config-history.py`.
- The installer already resolves it from the source side:
  `plugins/sd/installer/providerhistory.py` reads
  `HISTORY_SOURCE = Path("templates/docs/...")` relative to the installer ROOT.
  Only the audit looks in the consumer.
- The warning is advisory; audits still report `passed`. The cost is silent:
  a thin consumer holding a provider config that the installer will never
  refresh again is indistinguishable from one holding a current config, which
  is exactly the drift this check was written to surface.

## Requirements

- The audit must resolve the provider-config history from an authoritative
  source when the audited install is thin, rather than from the consumer.
- Keep the existing behavior for a fat install, where the consumer legitimately
  carries its own `docs/` copy: a fat consumer's own file stays authoritative.
- Preserve fail-safe reporting. If no history can be resolved from either
  location, the audit must still warn rather than silently claim the configs
  are current.
- Do not make the audit depend on being invoked from a source checkout when it
  is not: if the source-side history is genuinely unreachable, say so with the
  reason, as the current code does for the consumer-side path.

## Acceptance Criteria

- [ ] Auditing a thin consumer from a pack source checkout performs the
      provider-config currency check instead of warning that the history is
      absent.
- [ ] A thin consumer holding a stale but installer-recognized provider config
      is reported as behind, proven by a regression test.
- [ ] A fat consumer continues to be checked against its own `docs/` copy.
- [ ] With the history unreadable from every candidate location, the audit warns
      with the specific reason and does not report the configs as current.
- [ ] A full fleet audit pass over the current registry emits no
      "cannot check provider config currency" warning.
